EB-NeRD — see the EB-NeRD section below (sampled; rationale given there).

NOTE — the same change helps ranking and hurts retrieval.
Switching the query from "last 10 clicks" to the full click history RAISED
BM25's re-ranking AUC (0.5544 -> 0.5624, Q4 below) but LOWERED its
full-corpus recall@50 (0.0118 -> 0.0089). Both were measured, and the
divergence is real rather than noise. The mechanism: recall@K searches the
whole 130,379-article catalog, and a longer query matches more documents at
least once, so the top-50 fills with broadly-related articles and the
specific ones get pushed out. Re-ranking never has that problem — it only
orders ~40 candidates that were already curated, so extra query signal can
only help discriminate among them. The two tasks reward opposite things, and
a single "better query" setting does not exist for both.

Semantic wins on every accuracy metric on MIND, and the margin (+0.070 AUC)
is ~70x the width of the bootstrap CI, so it is not a sampling artifact.

WHICH SLICES: the gap is widest for warm users (0.6414 vs 0.5673 = +0.074)
and narrowest for cold-start users (0.5730 vs 0.5303 = +0.043). That
ordering is the expected one — both methods degrade without history, but
mean-pooled embeddings degrade more gracefully than term overlap, because a
single clicked article still yields a usable 384d direction whereas it
yields very few query terms.

BM25 wins only on intra-list diversity (0.7641 vs 0.7190). This is not a
point in its favour so much as a symptom: 10.0% of BM25's candidate scores
are exactly 0.0 (no term overlap at all) and 8.6% of candidates sit in a tie
group, so roughly a tenth of its ordering is arbitrary tie-breaking. Randomly
ordered items are, unsurprisingly, more "diverse" than deliberately ranked
ones.

THE HEAD/TAIL INVERSION (reproduced independently on both datasets and both
retrievers, so it is a property of the task, not of one model):
AUC is HIGHER on tail articles (semantic 0.6566 vs 0.6300; BM25 0.6034 vs
0.5584) while MRR and nDCG are much LOWER (semantic 0.2677 vs 0.3451).
These are not contradictory — they answer different questions. AUC asks
"can you separate clicked from unclicked?", and a tail impression is an
easier separation problem because its candidates are less uniformly
attractive. MRR/nDCG ask "is the right item at the very top?", which is
harder on tail impressions because the clicked article is genuinely obscure
and content similarity alone rarely lifts it to rank 1. A system tuned only
on AUC would look like it handles the long tail well while actually serving
it badly.

WHY EB-NeRD HAS NO COLD-START SLICE: the cold/warm split thresholds at <5
clicks, and EB-NeRD's history file guarantees a minimum history length of 5
(confirmed in the provided ebnerd_analysis.ipynb: min_history_len = 5). The
dataset therefore contains no cold-start users by construction, and the
"warm" row is necessarily identical to "all". Q4 requires at least one
slice; head/tail is the informative one for this dataset and is reported
above for MIND and below for EB-NeRD. This is a property of the data, not a
harness bug — but it does mean cold-start behaviour cannot be studied on
EB-NeRD at all, only on MIND.

--- ANN index: what we ship, and what the alternatives actually cost ---
  python -m src.evaluation.benchmark_index --dataset mind --n-queries 1000
  MIND corpus: 130,379 vectors x 384d. Latency is per single query (serving
  shape); batch_qps is throughput when queries arrive together (offline
  shape). recall@100 is measured AGAINST THE EXACT FLAT RESULT, i.e. "does
  this index return the neighbours exhaustive search would have returned".

  index                              build_s  size_MB  latency_ms  p95_ms  batch_qps  recall@100_vs_exact
  IndexFlatIP (exact, SHIPPED)       0.07     200.3    2.704       3.67    5,151      1.0000
  IndexIVFFlat nlist=1024 nprobe=1   2.66     202.9    0.055       0.079   102,699    0.3728
  IndexIVFFlat nlist=1024 nprobe=8   2.24     202.9    0.094       0.120   38,834     0.7550
  IndexIVFFlat nlist=1024 nprobe=32  2.32     202.9    0.229       0.286   13,653     0.9060
  IndexHNSWFlat M=32 efSearch=32     9.31     235.8    0.290       0.455   22,666     0.8312
  IndexHNSWFlat M=32 efSearch=128    8.96     235.8    0.617       0.881   11,318     0.9644

  Reading: IVF at nprobe=1 is 49x faster than exact search but discards 63%
  of the true neighbours — the classic trap of quoting a speedup without its
  recall. Raising nprobe walks the frontier back (nprobe=32: 11.8x faster,
  90.6% agreement). HNSW dominates IVF on the accuracy side at comparable
  latency (efSearch=128: 4.4x faster than exact, 96.4% agreement) but costs
  ~130x the build time and +35MB on disk.

  WHY WE SHIP EXACT ANYWAY — the decisive point is that our serving path
  never queries the index. Codabench supplies the candidate list, so
  submissions go through score_candidates(), which scores the ~12-40 named
  articles directly. The FAISS index is exercised only by Q2/Q3's
  full-corpus recall@K, an offline batch job where 5,151 q/s is ample. So an
  approximate index would trade 4-63% of true neighbours for latency we have
  no use for, and would additionally make recall@K a measurement of the
  index's approximation error rather than of the retrieval method. Exact
  search is the correct choice *for this workload*; on a serving path that
  did hit the index per request, HNSW at efSearch=128 is where we would go.

--- Scoring path: measured cost of every optimization ---
  python -m src.evaluation.benchmark_retrieval --dataset mind --n 1000
  1,000 MIND val impressions, mean history 33.8 articles, mean candidates 40.6.

  path                                          mean_ms  p50_ms  p95_ms  per_sec
  BM25 score_candidates (shipped)               0.528    ~0.30   ~2.0    1,894
  Semantic score_candidates (shipped)           0.051    ~0.03   ~0.13   19,608
  BM25 via full-corpus get_scores (REJECTED)    14.111   14.29   18.678  71
  Semantic via full-corpus matvec (REJECTED)    3.875    3.253   6.343   258
  BM25 without token memoization                2.681    1.606   8.974   373

  1. TARGETED vs FULL-CORPUS SCORING — 27x (BM25) and 76x (semantic).
     The naive way to score an impression is to score the entire catalog and
     read off the candidates. It gives identical rankings and is the single
     most expensive mistake available here: 14.1ms vs 0.528ms per impression.
     Over EB-NeRD's 13.5M-impression test set that is ~53 hours vs ~2 hours.

  2. QUERY-TOKEN MEMOIZATION — 5.1x on BM25 (2.681 -> 0.528ms).
     Article tokens never change, but popular articles recur across many
     users' histories, and the pre-fix code re-tokenized and re-STEMMED each
     user's entire history on every impression. Caching tokens per article
     removes ~77% of all work score_candidates did.

  3. TWO OPTIMIZATIONS THAT WERE ACTUALLY PESSIMIZATIONS (and why).
     Both were argued from asymptotics and both made things slower until
     measured:

       BM25 IDF vector          mean_ms      Semantic candidate gather   mean_ms
       np.zeros(V) per call     0.717        per-candidate Python loop   0.062
       reused buf, Python loops 0.938  WORSE np.full + Python fill loop  0.077  WORSE
       reused buf, vectorized   0.147  BEST  list-comp -> np.array       0.034  BEST

     The BM25 argument was "avoid an O(V) memset per impression, ~550GB of
     zeroing across the test set". That reasoning is wrong: np.zeros is a
     C-level calloc (frequently lazily-zeroed pages), so the memset was
     nearly free, while the Python loop introduced to CLEAR the reused buffer
     ran over every unique query term and cost more than it saved. The
     semantic argument was "avoid ~95M individual np.dot calls"; also wrong,
     because gathering 40x384 floats copies real memory and the win only
     appears once the index array is built in one shot.
     The optimizations are real — 4.9x and 1.8x respectively — but the source
     of the win was VECTORIZING THE INDEX CONSTRUCTION, not avoiding the
     allocation. Verified score-identical after the fix (BM25 max abs diff
     0.0; semantic 8.9e-08, i.e. float32 epsilon).

FEATURES UNAVAILABLE AT SERVING TIME: none are used. The only inputs to
either retriever are article text (title/abstract/body) and the user's prior
click history, both of which exist at serving time. We deliberately do NOT
use article popularity, total_inviews/total_pageviews, read_time,
scroll_percentage, or next_read_time — the last three are present in
EB-NeRD's training behaviours but absent from its test set precisely because
they are post-hoc. So the "with and without serving-time-unavailable
features" comparison degenerates: there is no "with" configuration to report.

BEHAVIOUR-WINDOW BOUNDARY: enforced and now actually tested. Previously the
test module's docstring claimed to assert this while no test did — the claim
was removed and two real tests added. EB-NeRD is checked directly against
article publication timestamps (5,437,152 history entries checked, 0
published after their impression). MIND has no publication timestamps at all
(published_time null for all 130,379 articles), so it is checked structurally
instead: a user's history may only grow over time (6,288 multi-impression
users checked, 0 violations).

Reproducibility notes
=====================================================================
- One-command rebuild:  python build_pipeline.py --dataset both
- Sampling is always seeded (--sample-n N --seed 42) so any sampled figure
  above can be reproduced exactly.
- Caches are fingerprinted on content AND on processing config: the BM25
  index stores TOKENIZER_VERSION, the embedding store EMBEDDING_MODEL_VERSION.
  Changing tokenization or the embedding model invalidates them automatically
  rather than silently serving incompatible vectors.
- BM25 index persistence stores plain arrays, not a pickled class instance.
  The earlier version pickled the live FastBM25 object, which records its
  class as "__main__.FastBM25" when built via `python -m src.retrieval.bm25`
  and could then not be loaded from any other entry point — generate_preds.py
  and metrics.py both died with AttributeError on it.
