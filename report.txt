Question 1: Reproducible Data Pipeline
  python build_pipeline.py --dataset both
=====================================================================

The single command runs: download -> parse into a unified schema -> temporal
split -> feature store. Both datasets are normalised to ONE internal schema at
the edge, so every downstream component (BM25, semantic, eval harness,
submission generator) contains zero dataset-specific branching:

  articles      article_id, title, abstract, body, category, entities, published_time
  impressions   impression_id, user_id, timestamp, click_history, candidates, labels

Field mapping is not trivial: EB-NeRD has no "abstract" (its subtitle is used),
no binary label vector (article_ids_clicked is a list of clicked ids, expanded
against article_ids_inview), and keeps history in a separate history.parquet
keyed by user, whereas MIND embeds it inline per row and encodes labels as a
"-1"/"-0" suffix on each candidate.

--- Split sizes actually produced ---
                              MIND            EB-NeRD
  articles                 130,379            125,541
  train                  1,801,223         20,752,525
  val                      431,511          1,997,301
  test                     376,485          1,880,449
  competition test       2,370,727         13,536,710

TEMPORAL SPLIT, NEVER RANDOM. Cutoffs are anchored to the end of the data:
  test_cutoff = max(timestamp) - test_days      val_cutoff = test_cutoff - val_days
  train: t < val_cutoff   val: val_cutoff <= t < test_cutoff   test: t >= test_cutoff
Anchoring at the END (rather than the start) means the evaluation window is the
most recent data, which is the closest available proxy for "next week". The
competition test set is kept entirely OUT of this split — it is unlabeled and
exists only to generate submissions.

FEATURE STORE. build_article_store / build_user_store / build_embedding_index
cache the expensive invariants (article features, per-user history, embeddings)
so retrieval and evaluation never recompute them. See "Reproducibility notes"
at the end of this file for how staleness is detected.

MEMORY MODEL. The split is the part that does not fit in RAM: EB-NeRD's
behaviours are 12M+ rows with list-valued columns, and pandas materialises each
list cell as an individual Python object, so peak memory exceeded 16GB on a
6.75GB file. Polars scan_parquet -> sink_parquet executes the split as a lazy
plan in Arrow batches instead, and the user store was ultimately built as a
manual reduction over parquet row groups into a plain dict — memory
proportional to unique users only, and predictable regardless of what else is
running on the machine.

EB-NeRD — see the EB-NeRD section below (sampled; rationale given there).

NOTE — the same change helps ranking and hurts retrieval.
Switching the query from "last 10 clicks" to the full click history RAISED
BM25's re-ranking AUC (0.5544 -> 0.5624, Q4 below) but LOWERED its
full-corpus recall@50 (0.0118 -> 0.0089). Both were measured, and the
divergence is real rather than noise. The mechanism: recall@K searches the
whole 130,379-article catalog, and a longer query matches more documents at
least once, so the top-50 fills with broadly-related articles and the
specific ones get pushed out. Re-ranking never has that problem — it only
orders ~40 candidates that were already curated, so extra query signal can
only help discriminate among them. The two tasks reward opposite things, and
a single "better query" setting does not exist for both.

ordered items are, unsurprisingly, more "diverse" than deliberately ranked
ones.

THE HEAD/TAIL INVERSION on MIND (see the EB-NeRD section for why this is
NOT a universal property — it reverses there for the semantic retriever):
AUC is HIGHER on tail articles (semantic 0.6566 vs 0.6300; BM25 0.6034 vs
0.5584) while MRR and nDCG are much LOWER (semantic 0.2677 vs 0.3451).
These are not contradictory — they answer different questions. AUC asks
"can you separate clicked from unclicked?", and a tail impression is an
easier separation problem because its candidates are less uniformly
attractive. MRR/nDCG ask "is the right item at the very top?", which is
harder on tail impressions because the clicked article is genuinely obscure
and content similarity alone rarely lifts it to rank 1. A system tuned only
on AUC would look like it handles the long tail well while actually serving
it badly.

THE RETRIEVERS SWAP PLACES BETWEEN THE TWO TASKS. On EB-NeRD, BM25 beats
semantic ~10x on recall@K yet loses by 0.073 AUC on re-ranking. On MIND,
semantic wins both. Taking either dataset alone would have produced a
confident and wrong general conclusion about which method is better.

                MIND BM25   MIND semantic   EB-NeRD BM25   EB-NeRD semantic
  recall@50     0.0089      0.0125          0.0042         0.0004
  AUC           0.5624      0.6324          0.4768         0.5499

The mechanism is the same mean-pooling limitation seen throughout: averaging
267 article vectors yields a profile generic enough to order 12 known
candidates but far too diffuse to locate one specific article in a
125,541-article catalog. BM25's rare-term matching still fires on specific
vocabulary and so retrieves better, even though its ranking of an already-
curated list is anti-correlated with clicks.

ABLATION — should the embedded text include the article BODY? (rejected)
EB-NeRD is the only dataset with full body text, and the semantic retriever
embeds only title+abstract while BM25 indexes title+abstract+body. Tested
directly on the fixed 20,000-impression sample, same corpus, same model, only
the embedded string varying:

  condition                     AUC       encode time (125,541 articles)
  title + abstract (shipped)    0.5574    186s
  title + abstract + body       0.5514    635s
  delta                        -0.0060    3.4x slower

Rejected on both axes: it costs 3.4x the encoding time to LOSE 0.006 AUC.

WHY, and why this is not merely a null result. The encoder's max_seq_length is
128 tokens and title+abstract already consumes ~40 (mean 148 characters), so
appending a 2,259-character mean body does not embed the article — it embeds
roughly its first 80 tokens and discards ~80% of it. What actually got added
was an arbitrary truncation of the lede, and Danish news ledes are formulaic
(attribution, dateline, scene-setting), so they dilute the topical signal that
the headline and standfirst carry densely without adding proportionate
information.

The generalisable claim: MORE TEXT IS NOT MORE SIGNAL WHEN THE ENCODER HAS A
FIXED TOKEN BUDGET. Title and abstract are editorially compressed summaries and
therefore the highest information density per token available in the document;
spending a fixed budget on lower-density text is a net loss. This is a
statement about matching input to model capacity, not about news.

It also sharpens the lexical/semantic contrast already reported here: BM25 uses
the body and benefits from it, because a sparse inverted index has no length
budget — every term is indexed regardless of document length. The two families
have genuinely different appetites for text, and this measures the difference
rather than assuming it. Note the corollary: this result is specific to a
128-token encoder. A long-context embedding model could plausibly reverse it,
which is the obvious follow-up if more compute were available.

FULL-HISTORY TRADE-OFF, CONFIRMED ON BOTH DATASETS AND BOTH RETRIEVERS:
switching from last-10 to the full click history improved re-ranking every
time (MIND BM25 0.5544->0.5624, MIND semantic 0.6194->0.6324, EB-NeRD
semantic 0.5469->0.5574) while reducing full-corpus recall every time
(MIND BM25 recall@50 0.0118->0.0089; EB-NeRD semantic 0.0008->0.0004).
There is no single "better history length" — the two tasks want opposite
things, and any system doing both needs to configure them separately.

WHY EB-NeRD HAS NO COLD-START SLICE: the cold/warm split thresholds at <5
clicks, and EB-NeRD's history file guarantees a minimum history length of 5
(confirmed in the provided ebnerd_analysis.ipynb: min_history_len = 5). The
dataset therefore contains no cold-start users by construction, and the
"warm" row is necessarily identical to "all". Q4 requires at least one
slice; head/tail is the informative one for this dataset and is reported
above for MIND and below for EB-NeRD. This is a property of the data, not a
harness bug — but it does mean cold-start behaviour cannot be studied on
EB-NeRD at all, only on MIND.

--- ANN index: what we ship, and what the alternatives actually cost ---
  python -m src.evaluation.benchmark_index --dataset mind --n-queries 1000
  MIND corpus: 130,379 vectors x 384d. Latency is per single query (serving
  shape); batch_qps is throughput when queries arrive together (offline
  shape). recall@100 is measured AGAINST THE EXACT FLAT RESULT, i.e. "does
  this index return the neighbours exhaustive search would have returned".

  index                              build_s  size_MB  latency_ms  p95_ms  batch_qps  recall@100_vs_exact
  IndexFlatIP (exact, SHIPPED)       0.07     200.3    2.704       3.67    5,151      1.0000
  IndexIVFFlat nlist=1024 nprobe=1   2.66     202.9    0.055       0.079   102,699    0.3728
  IndexIVFFlat nlist=1024 nprobe=8   2.24     202.9    0.094       0.120   38,834     0.7550
  IndexIVFFlat nlist=1024 nprobe=32  2.32     202.9    0.229       0.286   13,653     0.9060
  IndexHNSWFlat M=32 efSearch=32     9.31     235.8    0.290       0.455   22,666     0.8312
  IndexHNSWFlat M=32 efSearch=128    8.96     235.8    0.617       0.881   11,318     0.9644

  Reading: IVF at nprobe=1 is 49x faster than exact search but discards 63%
  of the true neighbours — the classic trap of quoting a speedup without its
  recall. Raising nprobe walks the frontier back (nprobe=32: 11.8x faster,
  90.6% agreement). HNSW dominates IVF on the accuracy side at comparable
  latency (efSearch=128: 4.4x faster than exact, 96.4% agreement) but costs
  ~130x the build time and +35MB on disk.

  WHY WE SHIP EXACT ANYWAY — the decisive point is that our serving path
  never queries the index. Codabench supplies the candidate list, so
  submissions go through score_candidates(), which scores the ~12-40 named
  articles directly. The FAISS index is exercised only by Q2/Q3's
  full-corpus recall@K, an offline batch job where 5,151 q/s is ample. So an
  approximate index would trade 4-63% of true neighbours for latency we have
  no use for, and would additionally make recall@K a measurement of the
  index's approximation error rather than of the retrieval method. Exact
  search is the correct choice *for this workload*; on a serving path that
  did hit the index per request, HNSW at efSearch=128 is where we would go.

--- Scoring path: measured cost of every optimization ---
  python -m src.evaluation.benchmark_retrieval --dataset mind --n 1000
  1,000 MIND val impressions, mean history 33.8 articles, mean candidates 40.6.

  path                                          mean_ms  p50_ms  p95_ms  per_sec
  BM25 score_candidates (shipped)               0.528    ~0.30   ~2.0    1,894
  Semantic score_candidates (shipped)           0.051    ~0.03   ~0.13   19,608
  BM25 via full-corpus get_scores (REJECTED)    14.111   14.29   18.678  71
  Semantic via full-corpus matvec (REJECTED)    3.875    3.253   6.343   258
  BM25 without token memoization                2.681    1.606   8.974   373

  1. TARGETED vs FULL-CORPUS SCORING — 27x (BM25) and 76x (semantic).
     The naive way to score an impression is to score the entire catalog and
     read off the candidates. It gives identical rankings and is the single
     most expensive mistake available here: 14.1ms vs 0.528ms per impression.
     Over EB-NeRD's 13.5M-impression test set that is ~53 hours vs ~2 hours.

  2. QUERY-TOKEN MEMOIZATION — 5.1x on BM25 (2.681 -> 0.528ms).
     Article tokens never change, but popular articles recur across many
     users' histories, and the pre-fix code re-tokenized and re-STEMMED each
     user's entire history on every impression. Caching tokens per article
     removes ~77% of all work score_candidates did.

  3. TWO OPTIMIZATIONS THAT WERE ACTUALLY PESSIMIZATIONS (and why).
     Both were argued from asymptotics and both made things slower until
     measured:

       BM25 IDF vector          mean_ms      Semantic candidate gather   mean_ms
       np.zeros(V) per call     0.717        per-candidate Python loop   0.062
       reused buf, Python loops 0.938  WORSE np.full + Python fill loop  0.077  WORSE
       reused buf, vectorized   0.147  BEST  list-comp -> np.array       0.034  BEST

     The BM25 argument was "avoid an O(V) memset per impression, ~550GB of
     zeroing across the test set". That reasoning is wrong: np.zeros is a
     C-level calloc (frequently lazily-zeroed pages), so the memset was
     nearly free, while the Python loop introduced to CLEAR the reused buffer
     ran over every unique query term and cost more than it saved. The
     semantic argument was "avoid ~95M individual np.dot calls"; also wrong,
     because gathering 40x384 floats copies real memory and the win only
     appears once the index array is built in one shot.
     The optimizations are real — 4.9x and 1.8x respectively — but the source
     of the win was VECTORIZING THE INDEX CONSTRUCTION, not avoiding the
     allocation. Verified score-identical after the fix (BM25 max abs diff

  The 2026-08-25 submission scored 0.5404 after roughly 24 hours in the

  resolves it against our own hypothesis.

  WHAT WE GOT WRONG. When no EB-NeRD submission had scored, we found that the
  test set has 13,536,710 rows but only 13,336,711 distinct impression_ids
  (its 200,000 "beyond-accuracy" rows all carry impression_id = 0), noted that
  the course-provided ebnerd_analysis.ipynb groups by impression_id and emits
  13,336,711 lines, and inferred that our one-line-per-ROW file was the cause.
  We implemented --unique-ids to match the notebook.

  That inference was WRONG. The submission that scored (901595) is the full
  13,536,710-line file, one line per row, exactly as originally generated. The
  format was accepted. The only cause of the missing score was queue latency —
  consistent with the course announcement that the organiser-hosted Docker
  evaluator is a bottleneck, and with the competition's own note that scoring
  "can take up to a few hours" and that debug logs are withheld during the
  competition.

  The --unique-ids file was therefore NOT submitted: dropping 200,000 rows
  would break the row-order alignment the guidelines explicitly require ("the
  row orders of the results should be consistent with those in the original
  files"). The flag remains in the code, documented as the notebook-matching
  variant, but the row-aligned file is the correct one.

  The methodological lesson is worth more than the format detail: a plausible
  mechanism was identified for a symptom, was consistent with a real
  discrepancy against the reference notebook, and was still not the cause. The
  symptom ("submitted, no score") never actually discriminated between "our
  file is malformed" and "the queue is slow", and we had no way to observe the
  difference because the platform withholds scoring logs during the
  competition. The right conclusion at the time would have been to state both
  hypotheses and wait, rather than to act on the more interesting one.

  OFFLINE vs ONLINE — the harness is validated on both datasets.

    EB-NeRD   0.5496              0.5404                     -0.009
  Both gaps are under 0.02, and the method ordering is preserved on both
  leaderboards (semantic > BM25). This is the real check on Q4: an offline
  harness is only worth having if it predicts the held-out result, and here
  it does, in both directions and in two languages. Note the gap has opposite
  SIGN on the two datasets, which argues against a systematic optimism bias
  in the harness — the more common failure mode when offline consistently

Reproducibility notes
=====================================================================
- One-command rebuild:  python build_pipeline.py --dataset both
- Sampling is always seeded (--sample-n N --seed 42) so any sampled figure
  above can be reproduced exactly.
- Caches are fingerprinted on content AND on processing config: the BM25
  index stores TOKENIZER_VERSION, the embedding store EMBEDDING_MODEL_VERSION.
  Changing tokenization or the embedding model invalidates them automatically
  rather than silently serving incompatible vectors.
- BM25 index persistence stores plain arrays, not a pickled class instance.
  The earlier version pickled the live FastBM25 object, which records its
  class as "__main__.FastBM25" when built via `python -m src.retrieval.bm25`
  and could then not be loaded from any other entry point — generate_preds.py
  and metrics.py both died with AttributeError on it.
